## Team Receipt M2.3 evidence for issue #98

**Owner and source.** Gwantana Kiboigo is the assignee for [issue #98](https://github.com/gwan-kib/COSC-310-Lab-Food4Thought/issues/98) under M2 §5. The evidence uses M1's working frontend as the starting point for M2 integration.

**Observed weakness.** Discovery's [`getJson`](https://github.com/gwan-kib/COSC-310-Lab-Food4Thought/blob/f142e6ba41aa0fe74e3a3586113835eb41d0aaf6/frontend/app.js#L13-L33), [Create restaurant's submission handler](https://github.com/gwan-kib/COSC-310-Lab-Food4Thought/blob/f142e6ba41aa0fe74e3a3586113835eb41d0aaf6/frontend/create-restaurant.js#L74-L99), and Edit restaurant's [`fetchWithTimeout`](https://github.com/gwan-kib/COSC-310-Lab-Food4Thought/blob/f142e6ba41aa0fe74e3a3586113835eb41d0aaf6/frontend/edit-restaurant.js#L64-L85) each negotiate JSON and decode response bodies. Create and Edit also maintain separate 15-second abort timers. An additional M2 screen following these examples would have to choose or copy one of three implementations, making request changes and failure handling easier to miss across screens.

**Alternatives and decision.** Keeping the helpers per page minimizes migration work and leaves three transport implementations to maintain. A client that also owns endpoint methods, response validation, and user-facing errors could give screens a uniform interface, but would couple discovery, forms, and future workflows whose error and retry rules differ. The selected [shared ES module](../../frontend/api-client.js) handles headers, JSON encoding and decoding, and an optional deadline in one place. It exposes `ok`, `status`, and `body` so each page can interpret the result. The existing static server loads it through standard browser modules without a build step.

**Result and trade-off.** One implementation now serves all three pages. Discovery still handles stale selections and independent menu errors. The forms still interpret 422 field errors and confirm writes against the expected status and payload. Create and Edit still use a 15-second deadline through body reading, and an uncertain write requires user verification before retry. Discovery retains its existing untimed reads. Endpoint paths, payload schemas, backend rules and storage are unaffected. Keeping page-specific decisions local leaves some repeated error formatting and validation rendering, which are outside this transport change.

**Review follow-up.** Thomas Chen identified that the transport needed to accept `Authorization` for reuse by protected M2 screens. The caller can now supply headers, and the client fills in missing JSON headers. This keeps token ownership with the caller and supports the [agreed bearer transport](../AUTH_DESIGN.md#agreed-policy-decisions). [Thomas's review](https://github.com/gwan-kib/COSC-310-Lab-Food4Thought/pull/112#pullrequestreview-5985511805) also identified the provenance conflict resolved when integrating `main`.

**Verification and review.** The [discovery characterization cases](../../tests/browser/test_frontend_browser.py) cover a rejected request and non-JSON and empty-detail HTTP errors. On Python 3.12 with required Chromium tests, `python -m pytest -x -q tests/browser tests/test_frontend.py` passed 42 tests against the pre-refactor code with the new characterization cases. The original refactor passed all 428 tests. The [header regression test](../../tests/browser/test_api_client_browser.py) failed before the follow-up because the request lacked `Authorization`, then passed with both the caller's header and the default JSON `Accept` header. After integrating `main`, `python -m pytest -q` passed all 466 tests with Chromium required. [PR #112](https://github.com/gwan-kib/COSC-310-Lab-Food4Thought/pull/112) records the check commands. Gwantana's review, teammate re-review, and merge evidence are pending.
