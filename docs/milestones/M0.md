## Application, architecture, and data

- [ ] A FastAPI application starts using the command documented in the root README.
- [ ] `GET /health` returns HTTP 200.
- [ ] A restaurant-list endpoint returns representative restaurant data. The brief shows `GET /restaurants` and permits an API prefix such as `/api/restaurants`; document the actual path.
- [ ] OpenAPI documentation is available at `/docs`.
- [ ] The restaurant operation follows Route → Service → Repository → JSON/CSV. Routes handle HTTP/API concerns, services handle application/business logic, and repositories access stored data. Routes do not read persistence files directly.
- [ ] Valid JSON and/or CSV contains at least two restaurants with stable identifiers and enough information for a meaningful response; data matches the application model.
- [ ] Pydantic defines typed restaurant fields and is used as the endpoint response model. Exact fields remain a provisional design decision; ID, name, and cuisine in the brief are examples, not a prescribed complete schema.
- [ ] Simple configuration allows the application and tests to use different persistence locations without machine-specific hard-coded paths.
- [ ] Dependencies are recorded in `requirements.txt` or `pyproject.toml`; the repository convention currently selects `requirements.txt`.

The brief suggests `app/api/routes/`, `app/services/`, `app/repositories/`, `app/schemas/`, `app/core/`, `app/main.py`, `data/`, `tests/`, `scrum/team-agreement.md`, `.gitignore`, a dependency file, and `README.md`. It permits another organization with a good reason, while the rubric refers to a “specific required structure.” **Recommendation:** follow the suggested layout where implemented responsibilities warrant it, and obtain clarification before relying on a materially different structure. Do not create unused placeholders to match it.
